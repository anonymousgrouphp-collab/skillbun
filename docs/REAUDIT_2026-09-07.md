## N1 — Production backend is down (New blocker) 🔴

**Live evidence.** Pages and static assets are healthy; every route that imports `firebaseAdmin` is not:

```
/                                       200  66117B   ✅
/roadmap                                200 201416B   ✅
/certificate/SKB-2026-CORP-LOR-Y5NH6M   200  45582B   ✅
/robots.txt · /sitemap.xml · /favicon.ico        200   ✅
/api/config                             200    102B   ✅  ← no firebaseAdmin import
/api/search?q=react                     200    109B   ✅  ← no firebaseAdmin import
/api/admin/certificates                 500      0B   🔴
/api/admin/analytics                    500      0B   🔴
/api/admin/workforce/employees          500      0B   🔴
/api/certify/mint                       500      0B   🔴
/api/certify/start · /api/certify/submit 500     0B   🔴
/api/docs/react/intro                   500      0B   🔴
/api/alumni/documents                   500      0B   🔴
```

The correlation is exact. I inventoried all 35 route files: **31 import `firebaseAdmin` and all 31 return 500**; the 4 that don't (`/api/config`, `/api/search`, `/api/human/verify`, `/api/admin/workforce/pdf/preview`) return 200.

**The same build is healthy locally.** I built HEAD (`exit 0`, 158 pages) and ran `next start`:

```
LOCAL /api/config                      200   ← same as prod
LOCAL /api/admin/certificates          401   ← correct auth denial, not a crash
LOCAL /api/docs/react/intro            401   ← correct
LOCAL /api/certify/start               401   ← correct
LOCAL /api/alumni/documents            200
```

So the code is fine. The lambda is dying on Vercel.

**Root cause.** `@google-cloud/firestore` is an **`optionalDependency`** of firebase-admin:

```js
// node_modules/firebase-admin/package.json
"optionalDependencies": { "@google-cloud/firestore": "^8.6.0", "@google-cloud/storage": "^7.19.0" }
// "dependencies": no @google-cloud/firestore
```

It is also listed in `serverExternalPackages`, which means Turbopack does **not** bundle it — it must be resolvable from `node_modules` inside the deployed function:

```js
// next.config.mjs:42
serverExternalPackages: ['firebase-admin', '@google-cloud/firestore', 'nodemailer'],
```

And it is **not a direct dependency** of the project:

```
@google-cloud/firestore      MISSING from dependencies
@google-cloud/storage        MISSING from dependencies
jose                         MISSING from dependencies
```

An optional transitive dependency of an externalized package is exactly the case that output-file tracing and production installs drop. When the module can't resolve at cold start, the function crashes before writing a response — which is precisely the `Content-Length: 0` 500 signature observed, with `x-matched-path` set and `x-vercel-cache: MISS` (routing succeeded, the function died).

**Fix — promote them to direct dependencies and redeploy:**

```bash
npm install @google-cloud/firestore@^8.6.0 @google-cloud/storage@^7.19.0 jose@^6.2.8
```

Then confirm the deployed function log shows no `MODULE_NOT_FOUND`. If any remains, drop `@google-cloud/firestore` from `serverExternalPackages` so it gets bundled instead.

**Before concluding, rule out the cheaper explanation:** check the Vercel runtime logs for the actual cold-start error and confirm `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, and `FIREBASE_PRIVATE_KEY` are set for the Production environment with real newlines in the key. Note that missing env vars alone would *not* produce this signature — `getAdminApp()` returns `null` gracefully and falls back to jose — which is what points at module resolution rather than configuration. The logs will settle it in one look.

## H1 — Alumni IDOR is still open 🔴

**Location:** [app/api/alumni/documents/route.js:10-26](../app/api/alumni/documents/route.js#L26) — unchanged.

```js
const rawQuery = (url.searchParams.get('query') || '').trim();
const token = authHeader.startsWith('Bearer ') ? authHeader.slice(7).trim() : '';
let userEmail = '';
if (token) {                                    // ← token is OPTIONAL
  try { … userEmail = decoded.email … }
  catch { /* Fallback to query */ }             // ← invalid token falls through
}
const searchQuery = (rawQuery || userEmail).toLowerCase();   // ← client wins
```

**Reproduced locally against HEAD, no `Authorization` header, arbitrary email:**

```
GET /api/alumni/documents?query=ceoharshpatel@gmail.com
→ 200 {"success":true,"count":3,"documents":[{
    "recipient_name":"Harsh Patel","recipient_email":"ceoharshpatel@gmail.com",
    "department":"Social Media & PR","designation":"Community & PR Intern",
    "start_date":"2026-08-18","end_date":"2026-09-18", …}]}
```

This route uses the admin SDK, so it bypasses the `workforce_docs` owner-only rule that Firestore correctly enforces. Anyone who knows an email address enumerates that person's credentials. It is masked on production right now only because of N1 — fixing N1 re-exposes it, so **fix both in the same deploy**.

**Fix:** require the token (401 when absent or invalid), and pin the search to the token's own email — allow `rawQuery` only when it is a reference code, never an arbitrary address:

```js
if (!token) return NextResponse.json({ error: 'Authentication required.' }, { status: 401 });
const decoded = await adminAuth.verifyIdToken(token);   // let failure 401, don't swallow
const userEmail = (decoded.email || '').toLowerCase();
const isRef = /^(sb|skb)[-/]/i.test(rawQuery);
const searchQuery = isRef ? rawQuery.toLowerCase() : userEmail;
```

## Confirmed fixes

### B1 — Admin bypass eliminated ✅

The `?adminEmail=` fallback is gone from all three files. Repo-wide grep for the pattern now returns **only** `app/api/certify/submit/route.js:126` (the dev bypass, see N3). `verifyAdminAuth` is now correct:

```js
if (!token) return 401 'Authentication required: Bearer token missing.'
const decoded = await adminAuth.verifyIdToken(token);
const isAdmin = await isUserAuthorizedAdmin(decoded);
if (isAdmin) return { authorized: true, … };
return 403 'Unauthorized: Admin privileges required.'
```

Rate limiting was added too — 30/min per user, 200/hr per IP, with `Retry-After` on 429. Local probe returns 401 with and without the parameter. (Production returns 500 for the N1 reason, so the live re-test of this specific fix is pending redeploy; the code and local behaviour are both correct.)

### B2 — Anonymous certificate enumeration closed ✅ (residual)

```
match /certificates/{certId} {
  allow get: if true;         // public verification by exact ID
  allow list: if signedIn();  // blocks anonymous REST enumeration
  allow write: if false;
}
```

**Live confirmation** — unauthenticated Firestore REST collection listing, previously 200 with PII:

```
certificates  403  ← was 200
examAttempts  403
```

`examAttempts` is also correctly scoped: `get` is owner-only (`resource.data.uid == request.auth.uid`), `list` is `isAdmin()`, `write: false`.

**Residual (Medium).** Two gaps remain against the original recommendation:

1. `allow list: if signedIn()` — `signedIn()` is only `request.auth != null`, so **any** registered user (self-serve signup) can still list the whole collection with `email`, `uid`, `department`, and `recommendation_text`. Use `isAdmin()` for `list`.
2. `allow get: if true` still returns the full document, including `email` and `uid`, to anyone with a certificate ID. Public verification needs name + status + issue date; drop the PII fields from the document or serve verification through a projecting server route.

### B3 — Server-side exam integrity ✅ (the standout fix)

This was rebuilt correctly rather than patched. The flow is now:

**`/api/certify/start`** — auth, rate limit, schema check, then `selectAndPrepareExamQuestions()` produces two records and stores the authoritative one in Firestore:

```js
// utils/server/certifyEngine.js:255 — server record (Firestore only)
serverQuestions.push({ index, question, options: shuffledOptions,
                       correctIndex: newCorrectIndex, explanation, difficulty });

// Sanitized client record (NO correctIndex, NO explanation)
clientQuestions.push({ index, question, options: shuffledOptions, difficulty });
```

Options are **re-shuffled per attempt** and `correctIndex` recomputed against the shuffle, so the answer key is unique to the attempt and never leaves the server. Only `clientQuestions` is returned (`:189`).

**`/api/certify/submit`** — verifies token → rate limits (10/min, 40/hr IP) → requires `attemptId` prefixed `att_` → loads the attempt → checks `attemptData.uid !== uid` → checks `status === 'ACTIVE'` → enforces `expiresAt` with a 15s latency grace (marking `EXPIRED` on overrun) → grades authoritatively via `gradeExamAttempt(attemptData.serverQuestions, answers)`.

**`/api/certify/mint`** — no longer accepts a score. It takes `attemptId`, and:

```js
if (attemptData.status !== 'COMPLETED' || !attemptData.passed) → reject
const verifiedScore = attemptData.score;   // read from the server's own grading
```

The self-reported-score path, the leaked answer key, and the localStorage progress gate are all gone. Replay is blocked by the one-shot `ACTIVE → COMPLETED` transition.

### H2 — Consent gating ✅

`app/components/ConsentBanner.jsx` now exists, and both analytics entry points are gated:

## New findings

### N2 — `jose` is a phantom dependency 🟠

[utils/server/firebaseAdmin.js:4](../utils/server/firebaseAdmin.js#L4) imports it, but it is in neither `dependencies` nor `devDependencies`. It resolves today only through npm hoisting:

```
skillbun@2.10.7
`-- firebase-admin@14.2.0
  `-- jwks-rsa@4.1.0
    `-- jose@6.2.8
```

Any firebase-admin minor bump that drops or re-scopes `jwks-rsa` breaks the auth fallback with no warning. Add it explicitly. Same class of fault as N1, and worth fixing in the same commit.

### N3 — `isDevBypass` awards a perfect score 🟡

[app/api/certify/submit/route.js:126](../app/api/certify/submit/route.js#L126):

```js
if (process.env.NODE_ENV === 'development' && isDevBypass) {
  correctCount = 10; score = 100; passed = true;
```

The `NODE_ENV` guard is correct and Next forces `production` in built output, so this is not currently exploitable. But it is a client-triggerable flag whose only defence is one env var, on the exact path B3 was opened up by. Strip it at build time or gate it behind a server-only secret rather than a request field.
