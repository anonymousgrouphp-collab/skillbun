# Web Security Fundamentals for Frontend Developers

As a frontend developer, understanding web security is paramount. While many critical security measures are implemented on the backend, a significant number of vulnerabilities can originate or be exploited directly on the client-side. This guide introduces fundamental web security concepts, common frontend vulnerabilities, and best practices to write more secure code.

## 1. Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is a type of security vulnerability typically found in web applications. XSS allows attackers to inject client-side scripts (e.g., JavaScript) into web pages viewed by other users. This can lead to various attacks, such as stealing session cookies, defacing websites, or redirecting users to malicious sites.

### How XSS Works

XSS exploits occur when a web application takes untrusted user input and outputs it directly to the browser without proper sanitization or encoding.

**Types of XSS:**

*   **Reflected XSS:** The malicious script is reflected off the web server, appearing in the response to the user's request. It's often delivered via a malicious link.
*   **Stored XSS:** The malicious script is permanently stored on the target server (e.g., in a database) and is then served to other users without proper encoding.
*   **DOM-based XSS:** The vulnerability lies in the client-side code itself, not necessarily in the server-side processing. The malicious payload is executed as a result of modifying the DOM environment in the victim's browser.

### Prevention

*   **Input Sanitization:** Validate and clean user input on both the client and server sides. Remove or escape potentially dangerous characters (`<`, `>`, `&`, `"`, `'`, `/`).
*   **Output Encoding:** Encode all untrusted data before outputting it into an HTML context. This converts characters like `<` to `&lt;`, preventing them from being interpreted as HTML tags.
*   **Content Security Policy (CSP):** Implement CSP via HTTP headers (`Content-Security-Policy`) to control which resources (scripts, styles, images) a user agent is allowed to load for a given page. This significantly reduces the attack surface for XSS.

**Example: Output Encoding in JavaScript**

```javascript
function escapeHtml(text) {
  var map = {
    '&': '&amp;',
    '<': '&lt;',
    '>': '&gt;',
    '"': '&quot;',
    "'": '&#039;'
  };
  return text.replace(/[&<>"]/g, function(m) { return map[m]; });
}

// Example usage:
const userInput = "<script>alert('You are hacked!');</script>";
document.getElementById('displayArea').innerHTML = escapeHtml(userInput);
// This will display the script as text, not execute it.
```

## 2. Cross-Site Request Forgery (CSRF)

Cross-Site Request Forgery (CSRF), also known as "Sea-Surf" or XSRF, is an attack that tricks a victim into submitting a malicious request to a web application they are currently authenticated to. Unlike XSS, which exploits trust in a website, CSRF exploits the trust a website has in the user's browser.

### How CSRF Works

An attacker crafts a malicious web page (e.g., an image tag or a hidden form) that sends a request to a legitimate web application. If the victim is logged into that application when they visit the malicious page, their browser will automatically include their authentication credentials (like session cookies) with the request. The application, seeing valid credentials, will process the malicious request as if it were legitimate.

**Example Scenario:**
1.  User logs into `bank.com`.
2.  Attacker sends a malicious link or embeds an `<img>` tag on a different site:
    ```html
    <img src="https://bank.com/transfer?amount=1000&toAccount=ATTACKER_ACCOUNT" style="display:none;">
    ```
3.  If the user visits the attacker's page while still logged into `bank.com`, their browser automatically sends the request to `bank.com` with their session cookies, potentially initiating an unauthorized transfer.

### Prevention

*   **CSRF Tokens:** The most common and effective defense. A unique, unpredictable, and secret token is generated by the server and included in every form submission or AJAX request that could modify state. The server then verifies this token upon submission.
*   **SameSite Cookies:** This attribute can be set on cookies (`Lax`, `Strict`, `None`). `SameSite=Lax` (default in modern browsers) prevents cookies from being sent with cross-site requests unless it's a top-level navigation with a safe HTTP method (GET). `SameSite=Strict` completely prevents cookies from being sent with any cross-site request.
*   **Referer Header Check:** While not foolproof (can be spoofed or missing), checking the `Referer` header to ensure requests originate from your own domain can add an extra layer of defense.

**Concept: CSRF Token Flow**

1.  **Server generates token:** When a user requests a form, the server embeds a unique CSRF token within a hidden field in the HTML form.
2.  **Client submits token:** When the user submits the form, the token is sent along with other form data.
3.  **Server verifies token:** The server checks if the received token matches the one stored in the user's session. If they don't match, the request is rejected.

```html
<!-- Example of a form with a CSRF token -->
<form action="/transfer" method="POST">
    <input type="hidden" name="_csrf" value="[SERVER_GENERATED_CSRF_TOKEN_HERE]">
    <label for="amount">Amount:</label>
    <input type="number" id="amount" name="amount">
    <button type="submit">Transfer</button>
</form>
```

## 3. Cross-Origin Resource Sharing (CORS)

Cross-Origin Resource Sharing (CORS) is a browser security feature that restricts web pages from making requests to a different domain than the one that served the web page. This is a relaxation of the **Same-Origin Policy (SOP)**, a fundamental security concept in web browsers, which prevents a document or script loaded from one origin from interacting with a resource from another origin.

### How CORS Works

When a web page tries to access resources (e.g., data from an API) from a different origin (different domain, protocol, or port), the browser initiates a CORS mechanism.

1.  **Simple Requests:** For certain "simple" requests (GET, HEAD, POST with specific `Content-Type`), the browser sends the request directly with an `Origin` header indicating where the request originated. The server then decides whether to allow it and responds with an `Access-Control-Allow-Origin` header if allowed.
2.  **Preflight Requests:** For "non-simple" requests (e.g., PUT, DELETE, custom headers), the browser first sends an `OPTIONS` request (the "preflight" request) to the server. This preflight asks the server if it's safe to send the actual request. If the server responds with appropriate CORS headers (`Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`), the browser proceeds with the actual request.

### Common CORS Headers

*   `Access-Control-Allow-Origin`: Specifies which origins are allowed to access the resource. Can be `*` (any origin) or a specific origin like `https://example.com`.
*   `Access-Control-Allow-Methods`: Specifies which HTTP methods are allowed (e.g., `GET, POST, PUT, DELETE`).
*   `Access-Control-Allow-Headers`: Specifies which HTTP headers are allowed in the actual request.
*   `Access-Control-Allow-Credentials`: Indicates whether the browser should send cookies or HTTP authentication credentials with the request.

**Example: Server-side CORS Configuration (Node.js/Express)**

```javascript
const express = require('express');
const cors = require('cors'); // npm install cors
const app = express();

// Basic usage: allow all origins
// app.use(cors());

// Advanced usage: allow specific origin(s)
app.use(cors({
  origin: 'https://www.myfrontendapp.com', // Only allow this origin
  methods: ['GET', 'POST'], // Allow only GET and POST requests
  allowedHeaders: ['Content-Type', 'Authorization'], // Allow specific headers
  credentials: true // Allow sending cookies/auth headers
}));

app.get('/api/data', (req, res) => {
  res.json({ message: 'This is secure data from the API!' });
});

app.listen(3000, () => {
  console.log('Server listening on port 3000');
});
```

## 4. General Frontend Security Best Practices

*   **Keep Libraries Updated:** Regularly update all third-party libraries and frameworks to patch known vulnerabilities. Use tools like `npm audit` or `yarn audit`.
*   **Avoid Storing Sensitive Data Locally:** Never store sensitive user information (passwords, private keys, financial details) directly in local storage, session storage, or client-side JavaScript variables.
*   **Use HTTPS Everywhere:** Always serve your application over HTTPS to encrypt communication between the client and server, preventing man-in-the-middle attacks.
*   **Secure Cookie Handling:**
    *   **`HttpOnly`:** Prevents client-side scripts from accessing cookies, mitigating XSS attacks.
    *   **`Secure`:** Ensures cookies are only sent over HTTPS.
    *   **`SameSite`:** Prevents browsers from sending cookies with cross-site requests, mitigating CSRF (as discussed).
*   **Principle of Least Privilege:** Grant only the necessary permissions to your frontend components and associated API keys.
*   **Input Validation:** Perform robust validation on all user inputs on both the frontend and backend.
