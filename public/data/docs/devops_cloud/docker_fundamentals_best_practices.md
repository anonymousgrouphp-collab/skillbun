# Docker Fundamentals & Best Practices

Docker has revolutionized how developers build, ship, and run applications. It provides a platform to package applications and their dependencies into standardized units called containers, ensuring consistency across various environments from development to production.

## 1. Core Docker Concepts

### 1.1 Docker Images
An **Image** is a lightweight, standalone, executable package that includes everything needed to run a piece of software, including the code, a runtime, libraries, environment variables, and config files. Images are built from a `Dockerfile` and are the blueprint for containers.

*   **Building Images:** `docker build -t myapp:1.0 .` (Builds an image named `myapp` with tag `1.0` from the current directory's Dockerfile).
*   **Pulling Images:** `docker pull ubuntu:latest` (Downloads an image from a registry, e.g., Docker Hub).

### 1.2 Docker Containers
A **Container** is a runnable instance of an image. You can create, start, stop, move, or delete a container. A container is isolated from the host system and other containers, making it portable and predictable.

*   **Running Containers:** `docker run -p 80:80 myapp:1.0` (Runs a container from `myapp:1.0`, mapping host port 80 to container port 80).
*   **Listing Containers:** `docker ps` (Shows running containers), `docker ps -a` (Shows all containers, including stopped ones).
*   **Stopping/Removing:** `docker stop <container_id_or_name>`, `docker rm <container_id_or_name>`.

### 1.3 Docker Volumes
By default, data inside a container is ephemeral; it's lost when the container is removed. **Volumes** provide a way to persist data generated by or used by Docker containers, decoupling data from the container's lifecycle.

*   **Bind Mounts:** Mounts a file or directory from the host machine into a container. Commonly used for development to allow host code changes to reflect inside the container instantly.
*   **Named Volumes:** Docker manages the creation, management, and storage location of these volumes. Best for persistent data storage in production environments.
    *   Example: `docker run -v mydata:/app/data myapp` (Mounts a named volume `mydata` to `/app/data` inside the container).

### 1.4 Docker Networks
Docker networking allows containers to communicate with each other and with the outside world. Each container gets its own network interface and IP address.

*   **Bridge Network (Default):** All containers without a specified network are attached to the default `bridge` network. Containers on the same bridge network can communicate with each other via IP addresses.
*   **Custom Bridge Networks:** Recommended for application stacks (e.g., a web app and a database) as they provide better isolation, DNS resolution by container name, and easier management.
    *   Example: `docker network create my-app-net` then `docker run --network my-app-net --name web-app myapp` and `docker run --network my-app-net --name db-server mydb`.

## 2. Dockerfile Best Practices

A `Dockerfile` is a text document that contains all the commands a user could call on the command line to assemble an image. Writing efficient and secure Dockerfiles is crucial.

### 2.1 Structure and Layering
Each instruction in a Dockerfile creates a read-only layer. When you change an instruction, only that layer and subsequent layers are rebuilt, leveraging Docker's cache. This impacts build speed and image size.

*   **Order instructions:** Place less frequently changing instructions (like `FROM`, `RUN apt-get update`) earlier in the Dockerfile to maximize cache hits.
*   **`.dockerignore`:** Use a `.dockerignore` file to exclude unnecessary files and directories (e.g., `node_modules`, `.git`, temporary files) from the build context. This speeds up the build process and reduces image size.

### 2.2 Multi-Stage Builds
Multi-stage builds allow you to use multiple `FROM` statements in your Dockerfile. Each `FROM` instruction can use a different base image, and you can selectively copy artifacts from one stage to another. This is crucial for creating small, secure production images by separating build-time dependencies (e.g., compilers, development tools) from runtime dependencies.

```dockerfile
# Stage 1: Build the application
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build --prod

# Stage 2: Create the final lightweight runtime image
FROM alpine:latest
WORKDIR /app
COPY --from=builder /app/dist ./dist # Only copy the built artifacts
COPY --from=builder /app/node_modules ./node_modules # Copy only production dependencies
COPY --from=builder /app/package.json ./package.json
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

### 2.3 Optimizing Image Size
*   **Choose a small base image:** Use `alpine` variants (e.g., `node:18-alpine`, `python:3.9-slim-buster`) whenever possible, as they are significantly smaller than their full counterparts.
*   **Combine `RUN` commands:** Chain multiple commands using `&&` and clean up temporary files (e.g., `apt-get clean`) in the same `RUN` instruction. This minimizes the number of layers and reduces overall image size.
*   **Remove build dependencies:** As shown in multi-stage builds, ensure that compilers, SDKs, and other development tools are not present in the final production image.

### 2.4 Security Considerations
*   **Run as a non-root user:** By default, containers run processes as the root user. Create a dedicated unprivileged user and switch to it using the `USER` instruction to mitigate potential security vulnerabilities if the container is compromised.
    ```dockerfile
    # ... previous instructions
    RUN addgroup -S appgroup && adduser -S appuser -G appgroup
    USER appuser
    CMD ["node", "dist/server.js"]
    ```
*   **Avoid sensitive information in images:** Do not hardcode secrets, API keys, or credentials directly in your Dockerfile or commit them into image layers. Use Docker secrets, environment variables (passed at runtime), or a secret management system.
