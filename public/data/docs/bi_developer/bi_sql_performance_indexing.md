## SQL Performance Tuning and Indexing: A Study Guide

Optimizing SQL query performance is a critical skill for any BI Developer, directly impacting the speed and responsiveness of data retrieval for analytical workloads. This guide covers essential techniques, from understanding execution plans to advanced indexing strategies and efficient query writing.

### 1. Understanding Execution Plans

An execution plan is a roadmap generated by the database engine that describes how it will execute a SQL query. Analyzing these plans is the first step in identifying performance bottlenecks.

**Core Concepts:**
*   **Table Scan:** The database reads every row in a table to find the desired data. This is often a sign of missing or ineffective indexes.
*   **Index Scan:** The database reads all entries in an index to find the desired data. More efficient than a table scan, but can still be improved.
*   **Index Seek:** The database quickly navigates directly to the specific rows using an index. This is generally the most efficient operation.
*   **Join Operations:** How tables are combined (e.g., Nested Loop, Hash Join, Merge Join). Understanding these helps optimize join conditions.

**How to Read Them:**
Execution plans graphically represent the sequence of operations. Look for operations that process large numbers of rows, use temporary tables, or perform full table scans. Tools like SQL Server Management Studio (SSMS), PostgreSQL's `EXPLAIN ANALYZE`, or MySQL's `EXPLAIN` are used to generate and interpret these plans.

**Example (PostgreSQL/MySQL):**
```sql
EXPLAIN ANALYZE
SELECT order_id, customer_name
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE order_date >= '2023-01-01';
```
This command will output the plan and execution statistics, allowing you to see actual row counts, costs, and execution times for each step.

### 2. Implementing Indexing Strategies

Indexes are special lookup tables that the database search engine can use to speed up data retrieval. They are crucial for improving `SELECT` query performance but come with overhead for `INSERT`, `UPDATE`, and `DELETE` operations.

**Types of Indexes:**
*   **Clustered Indexes:**
    *   Determines the physical order of data storage in the table. The data rows themselves are stored in the order of the clustered index keys.
    *   A table can have only one clustered index.
    *   Best used on primary key columns or columns frequently used in `ORDER BY` clauses or range queries.
    *   Example: A primary key on `CustomerID` will store all customer data physically sorted by `CustomerID`.

*   **Non-Clustered Indexes:**
    *   A separate structure that contains the indexed columns and pointers to the actual data rows.
    *   A table can have multiple non-clustered indexes.
