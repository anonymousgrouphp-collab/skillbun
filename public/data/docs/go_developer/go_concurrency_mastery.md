# Concurrency Mastery in Go\n\nGo's built-in concurrency model is a cornerstone of its appeal, allowing developers to build highly efficient and scalable applications. Unlike traditional thread-based concurrency, Go employs a lightweight and idiomatic approach using goroutines and channels, augmented by the powerful `context` package for advanced control.\n\n## 1. Understanding Concurrency vs. Parallelism\n\n*   **Concurrency**: Dealing with many things at once. It's about structuring a program such that it can handle multiple tasks independently, often overlapping in execution. Go achieves this with goroutines and channels.\n*   **Parallelism**: Doing many things at once. This requires multiple CPU cores and is about actual simultaneous execution of independent tasks. A concurrent program can be parallelized if sufficient resources are available. Go's runtime scheduler manages the mapping of goroutines to OS threads to achieve parallelism where possible.\n\n## 2. Goroutines: Go's Lightweight Concurrency Primitives\n\nGoroutines are functions or methods that run concurrently with other functions or methods. They are lightweight threads managed by the Go runtime, not the operating system. They have a small memory footprint (a few KB of stack space) and can grow or shrink as needed.\n\n### Creating a Goroutine\n\nSimply prepend the `go` keyword before a function call.\n\n```go\npackage main\n\nimport (\n\t"fmt"\n\t"time"\n)\n\nfunc sayHello(name string) {\n\ttime.Sleep(100 * time.Millisecond) // Simulate some work\n\tfmt.Printf("Hello, %s!\n", name)\n}\n\nfunc main() {\n\tgo sayHello("Alice") // Starts sayHello as a goroutine\n\tgo sayHello("Bob")   // Starts another goroutine\n\n\t// The main goroutine needs to wait for others to finish,\n\t// otherwise the program might exit before goroutines complete.\n\ttime.Sleep(200 * time.Millisecond)\n\tfmt.Println("Main goroutine finished.")\n}\n```\n\n**Explanation**: When `main` starts `sayHello("Alice")` and `sayHello("Bob")` as goroutines, it doesn't wait for them to complete. It continues its own execution. Without the `time.Sleep` in `main`, the program might exit before "Alice" and "Bob" have a chance to print, as the `main` goroutine is the parent of all other goroutines and the program exits when `main` finishes.\n\n## 3. Channels: Communicating Between Goroutines\n\nChannels are the primary way goroutines communicate and synchronize. They provide a safe and synchronized way to pass data between goroutines, adhering to Go's philosophy: "Do not communicate by sharing memory; instead, share memory by communicating."\n\n### Declaring and Using Channels\n\nChannels are typed conduits. Values of a specific type can be sent into them and received from them.\n\n*   **Declaration**: `ch := make(chan int)` (unbuffered) or `ch := make(chan int, 5)` (buffered channel with capacity 5).\n*   **Sending**: `ch <- value`\n*   **Receiving**: `value := <-ch` or `<-ch` (to discard value).\n*   **Closing**: `close(ch)` (indicates no more values will be sent). Receiving from a closed channel returns the zero value and a boolean `false` if no more values are present.\n\n```go\npackage main\n\nimport (\n\t"fmt"\n\t"time"\n)\n\nfunc worker(id int, jobs <-chan int, results chan<- int) {\n\tfor j := range jobs { // Loop until the 'jobs' channel is closed\n\t\tfmt.Printf("Worker %d started job %d\n", id, j)\n\t\ttime.Sleep(50 * time.Millisecond) // Simulate work\n\t\tfmt.Printf("Worker %d finished job %d\n", id, j)\n\t\tresults <- j * 2 // Send result back\n\t}\n}\n\nfunc main() {\n\tjobs := make(chan int, 10)\n\tresults := make(chan int, 10)\n\n\t// Start 3 workers\n\tfor w := 1; w <= 3; w++ {\n\t\tgo worker(w, jobs, results)\n\t}\n\n\t// Send 5 jobs\n\tfor j := 1; j <= 5; j++ {\n\t\tjobs <- j\n\t}\n\tclose(jobs) // Important: Close jobs channel when done sending\n\n\t// Collect all results\n\tfor a := 1; a <= 5; a++ {\n\t\t<-results // Blocking call, waits for each result\n\t}\n\tclose(results) // It's good practice to close results when done receiving\n\tfmt.Println("All jobs processed and results collected.")\n}\n```\n\n### `select` Statement\n\nThe `select` statement lets a goroutine wait on multiple communication operations. It blocks until one of its cases can proceed, then it executes that case. If multiple cases are ready, `select` picks one at random.\n\n```go\npackage main\n\nimport (\n\t"fmt"\n\t"time"\n)\n\nfunc main() {\n\tc1 := make(chan string)\n\tc2 := make(chan string)\n\n\tgo func() {\n\t\ttime.Sleep(1 * time.Second)\n\t\tc1 <- "one"\n\t}()\n\tgo func() {\n\t\ttime.Sleep(2 * time.Second)\n\t\tc2 <- "two"\n\t}()\n\n\tfor i := 0; i < 2; i++ {\n\t\tselect {\n\t\tcase msg1 := <-c1:\n\t\t\tfmt.Println("received", msg1)\n\t\tcase msg2 := <-c2:\n\t\t\tfmt.Println("received", msg2)\n\t\tcase <-time.After(500 * time.Millisecond): // Timeout case\n\t\t\tfmt.Println("timeout")\n\t\t}\n\t}\n}\n```\n**Explanation**: In this example, the `select` statement waits for either `c1` or `c2` to receive a message. It also has a `time.After` case that acts as a timeout. Initially, the timeout will trigger before "one" or "two" are sent. After "one" is sent, the `c1` case will execute. Eventually, "two" will be sent, and `c2`'s case will execute.\n\n## 4. Synchronization with `sync.WaitGroup`\n\nWhile channels are for communication, `sync.WaitGroup` is used to wait for a collection of goroutines to finish.\n\n*   `Add(delta int)`: Increments the counter by `delta`.\n*   `Done()`: Decrements the counter.\n*   `Wait()`: Blocks until the counter is zero.\n\n```go\npackage main\n\nimport (\n\t"fmt"\n\t"sync"\n\t"time"\n)\n\nfunc performTask(id int, wg *sync.WaitGroup) {\n\tdefer wg.Done() // Decrement counter when the goroutine finishes\n\tfmt.Printf("Worker %d starting\n", id)\n\ttime.Sleep(1 * time.Second)\n\tfmt.Printf("Worker %d finished\n", id)\n}\n\nfunc main() {\n\tvar wg sync.WaitGroup\n\tfor i := 1; i <= 3; i++ {\n\t\twg.Add(1) // Increment counter for each goroutine\n\t\tgo performTask(i, &wg)\n\t}\n\twg.Wait() // Block until all goroutines call Done()\n\tfmt.Println("All workers completed.")\n}\n```\n\n## 5. The `context` Package: Managing Goroutine Lifecycles\n\nThe `context` package provides a way to carry deadlines, cancellation signals, and other request-scoped values across API boundaries and between goroutines. It's crucial for controlling the lifecycle of goroutines, especially in complex applications like web servers.\n\n### Key Concepts\n\n*   `Context`: An interface that defines methods for cancellation, deadlines, and value propagation.\n*   `context.Background()`: Returns an empty context, typically used at the top of an application's call stack.\n*   `context.TODO()`: Also returns an empty context, used when you're unsure which context to use or when a context is not yet available.\n*   `context.WithCancel(parent Context)`: Returns a new `Context` and a `CancelFunc`. Calling `CancelFunc` cancels this context and all its children.\n*   `context.WithTimeout(parent Context, timeout time.Duration)`: Returns a new `Context` that is canceled after `timeout`.\n*   `context.WithValue(parent Context, key, val interface{})`: Returns a new `Context` with a key-value pair.\n\n### Cancellation Example\n\n```go\npackage main\n\nimport (\n\t"context"\n\t"fmt"\n\t"time"\n)\n\nfunc longRunningTask(ctx context.Context, taskID int) {\n\tfmt.Printf("Task %d started...\n", taskID)\n\tfor {\n\t\tselect {\n\t\tcase <-time.After(500 * time.Millisecond):\n\t\t\tfmt.Printf("Task %d working...\n", taskID)\n\t\tcase <-ctx.Done(): // Check for cancellation signal\n\t\t\tfmt.Printf("Task %d received cancellation signal: %v\n", taskID, ctx.Err())\n\t\t\treturn // Exit the goroutine\n\t\t}\n\t}\n}\n\nfunc main() {\n\tctx, cancel := context.WithCancel(context.Background())\n\n\tgo longRunningTask(ctx, 1)\n\n\ttime.Sleep(2 * time.Second)\n\tfmt.Println("Main goroutine: Sending cancellation signal...")\n\tcancel() // Cancel the context, signaling taskID 1 to stop\n\n\ttime.Sleep(1 * time.Second) // Give some time for the goroutine to react\n\tfmt.Println("Main goroutine finished.")\n}\n```\n\n**Explanation**: The `longRunningTask` goroutine periodically checks `ctx.Done()`. When `cancel()` is called in `main`, the `Done()` channel of the context is closed, signaling all goroutines listening to it to shut down gracefully. `ctx.Err()` provides the reason for cancellation (e.g., `context.Canceled` or `context.DeadlineExceeded`).\n\n## Checklist / Exercise\n\n1.  **Goroutine & Channel Fundamentals**: Write a Go program where `N` goroutines (e.g., 3) concurrently fetch URLs from a channel, process them (e.g., print the URL), and send a "done" signal to another channel.
