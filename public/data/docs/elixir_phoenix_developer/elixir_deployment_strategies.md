# Elixir Deployment Strategies

Deploying Elixir and Phoenix applications differs from traditional web applications due to the Erlang Virtual Machine (BEAM) and its OTP capabilities. Understanding these deployment strategies is crucial for building robust, scalable, and maintainable systems.

## 1. Elixir Releases

Elixir Releases provide a self-contained unit of code, including the Erlang/Elixir runtime, your application, and all its dependencies. This means you don't need to have Erlang/Elixir installed on the target machine.

### Core Concepts:
*   **Self-contained**: Everything needed to run the application is bundled.
*   **Pre-compiled**: The application is compiled ahead of time, reducing startup overhead.
*   **Hot Code Upgrades**: The BEAM allows for updating running code without restarting the application (though this is an advanced topic and less commonly used in simpler deployments).
*   **Configuration**: Runtime configuration typically handled via environment variables, often read using `config/runtime.exs`.

### Workflow (`mix release`):
1.  Configure `mix.exs` with `rel/config.exs` (often generated by `mix release.init`).
2.  Run `mix release` to build the release.
3.  Transfer the resulting tarball (`_build/prod/rel/your_app/releases/YOUR_VERSION/your_app.tar.gz`) to your server.
4.  Extract and run using `bin/your_app start`.

### Trade-offs:
*   **Pros**: Self-contained, faster startup, good for immutable deployments, enables hot upgrades.
*   **Cons**: Larger deployment artifacts (includes BEAM runtime), hot upgrades can be complex to manage reliably, requires careful handling of system-level dependencies (e.g., `inotify-tools`).

## 2. Deployment with Docker

Docker provides a lightweight, portable, and consistent environment for deploying applications. When combined with Elixir releases, it creates a powerful and reproducible deployment artifact.

### Why Docker for Elixir?
*   **Isolation**: Your application runs in its own isolated environment.
*   **Consistency**: Guarantees the same environment from development to production.
*   **Portability**: Easily move your application between different hosts or cloud providers.
*   **Multi-stage Builds**: Significantly reduces the final image size by separating build dependencies from runtime dependencies.

### Basic Dockerfile Structure (Multi-stage):

```dockerfile
# Stage 1: Build the release
FROM hexpm/elixir:1.16.0-erlang-26.2.2-alpine-3.19.1 AS builder

# Install build dependencies
RUN apk add --no-cache build-base git

WORKDIR /app

# Copy and install dependencies
COPY mix.exs mix.lock ./
RUN mix deps.get --only prod

# Copy application code
COPY priv priv
COPY lib lib
COPY config config
# COPY assets assets # if you have assets and need to digest them in the build stage

# Compile assets if needed (e.g., Phoenix static assets)
# RUN mix phx.digest

# Build the release
ENV MIX_ENV=prod
RUN mix release --overwrite

# Stage 2: Create the final production image
FROM alpine:3.19.1

# Install runtime dependencies if any (e.g., certs for HTTPS, system tools)
RUN apk add --no-cache openssl ncurses-libs

WORKDIR /app

# Copy the built release from the builder stage
COPY --from=builder /app/_build/prod/rel/your_app ./ # Adjust 'your_app' to your actual app name

# Set environment variables for runtime configuration
ENV PORT=4000
EXPOSE 4000

# Command to run the release
CMD ["/app/bin/your_app", "start"]
```

### Trade-offs:
*   **Pros**: Excellent reproducibility, environment consistency, scalable with orchestration tools, efficient resource usage with multi-stage builds.
*   **Cons**: Introduces a Docker learning curve, initial build times can be longer, increased artifact size compared to just an Elixir release (if not optimized well).

## 3. Cloud Platforms

Cloud platforms simplify infrastructure management, allowing developers to focus on application logic.

### a. Gigalixir
A Platform-as-a-Service (PaaS) specifically designed for Elixir and Phoenix applications, built on AWS.

*   **Features**: Managed Elixir runtime, automatic deployments, easy scaling, integrated PostgreSQL, support for hot upgrades.
*   **Workflow**: `git push gigalixir master` (similar to Heroku).
*   **Trade-offs**:
    *   **Pros**: Extremely easy to use for Elixir apps, managed infrastructure, supports Elixir-specific features (e.g., clustering).
    *   **Cons**: Vendor lock-in, potentially higher cost for larger deployments, less control over underlying infrastructure.

### b. Fly.io
A platform for running apps close to users, focusing on edge deployments and global distribution. It excels with Dockerized applications.

*   **Features**: Global distribution, low-latency deployments, managed Postgres, built-in load balancing and DDoS protection.
*   **Workflow**: `flyctl launch`, `flyctl deploy`. Requires a `Dockerfile` and `fly.toml` configuration.
*   **Trade-offs**:
    *   **Pros**: Excellent for global applications, highly performant due to edge network, cost-effective for many use cases.
    *   **Cons**: Requires familiarity with Docker and `flyctl` configuration, steeper learning curve than Gigalixir.

### c. Kubernetes (K8s)
An open-source container orchestration platform for automating deployment, scaling, and management of containerized applications (like those built with Docker).

*   **Features**: Automatic scaling, self-healing, rolling updates, service discovery, load balancing, secret management.
*   **Workflow**: Define deployments, services, and other resources using YAML manifests. Deploy with `kubectl apply -f your-manifest.yaml`.
*   **Trade-offs**:
    *   **Pros**: Highly scalable and resilient, cloud-agnostic, powerful ecosystem, ideal for complex microservice architectures.
    *   **Cons**: Significant operational complexity, high learning curve, requires dedicated DevOps expertise, often overkill for smaller applications.

## Choosing a Strategy

*   **Small/Medium Apps, Elixir-first**: Gigalixir for ease of use.
*   **Medium/Large Apps, Global Reach, Docker-friendly**: Fly.io for performance and control.
*   **Large, Complex Microservices, High Scalability**: Kubernetes with Docker.
*   **Any size, self-managed server**: Elixir Releases + Docker for consistency and portability.
