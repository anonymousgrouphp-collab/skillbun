# Security Best Practices in Elixir/Phoenix

Security is paramount in web development. Neglecting security can lead to data breaches, reputational damage, and financial losses. This guide outlines common web vulnerabilities and how to implement secure coding practices specifically within the Elixir/Phoenix ecosystem.

## Introduction to Web Security

Web applications are constantly targeted by malicious actors. Understanding common attack vectors and proactively implementing defenses is crucial. Elixir and Phoenix provide robust foundations for building secure applications, but developers must still adhere to best practices.

## Common Web Vulnerabilities and Phoenix Defenses

### 1. Cross-Site Request Forgery (CSRF)

*   **What it is:** An attacker tricks a user into submitting a malicious request to a web application where they are already authenticated. The request originates from an untrusted site but appears legitimate to the application because the user is logged in.
*   **How Phoenix Defends:** Phoenix automatically protects against CSRF using anti-CSRF tokens. Every form generated by `form_for` or `form_tag` includes a hidden input with a unique token. The server then validates this token upon submission. If the token is missing or invalid, Phoenix rejects the request.

    **Example in Phoenix (HTML template):**

    ```html
    <%= form_for @changeset, Routes.user_path(@conn, :create), fn f -> %>
      <%= csrf_input_tag() %>
      <div class="form-group">
        <%= label f, :username %>
        <%= text_input f, :username, class: "form-control" %>
      </div>
      <div class="form-group">
        <%= label f, :password %>
        <%= password_input f, :password, class: "form-control" %>
      </div>
      <%= submit "Register", class: "btn btn-primary" %>
    <% end %>
    ```

### 2. SQL Injection

*   **What it is:** An attacker inserts or "injects" malicious SQL code into input fields (e.g., login forms, search bars) to execute arbitrary database commands, bypassing intended security measures. This can lead to unauthorized data access, modification, or deletion.
*   **How Phoenix/Ecto Defends:** Ecto, Elixir's database wrapper, inherently prevents most SQL injection attacks by using **parameterized queries** (also known as prepared statements). Instead of concatenating user input directly into SQL strings, Ecto separates the SQL command from the data. The database then understands which parts are code and which are data, preventing user input from being executed as SQL.

    **Conceptual Example (what Ecto prevents):**

    ```elixir
    # DANGEROUS (if not using Ecto.Query):
    # user_input = "' OR '1'='1" # Malicious input
    # query = "SELECT * FROM users WHERE username = '#{user_input}' AND password = '#{password}'"
    ```

    **SAFE (using Ecto.Query):**

    ```elixir
    # Ecto automatically parameterizes queries
    Repo.get_by(User, username: user_input)

    # Or when building queries:
    from u in User, where: u.username == ^user_input
    |> Repo.all()
    ```
    The `^` operator in Ecto explicitly marks a value as a parameter, ensuring it's safely escaped by the underlying database driver.

### 3. Authentication and Authorization

*   **Authentication:** Verifying a user's identity (e.g., username and password).
    *   **Secure Password Handling:** Always hash passwords before storing them. Never store plain-text passwords. Use strong, adaptive hashing algorithms like Argon2 or Bcrypt (libraries like `Comeonin` or `Phx.Gen.Auth` handle this). Include a salt to protect against rainbow table attacks.
    *   **Session Management:** Use secure session cookies. Ensure they are `secure` (sent only over HTTPS) and `httponly` (not accessible via client-side JavaScript) to mitigate XSS risks.

*   **Authorization:** Determining what an authenticated user is allowed to do.
    *   Implement **Role-Based Access Control (RBAC)** or **Policy-Based Authorization** to define permissions clearly. Phoenix contexts and plugs are excellent for enforcing authorization rules.
    *   Always verify user permissions on the server-side for every sensitive action.

### 4. Cross-Site Scripting (XSS)

*   **What it is:** Injecting malicious client-side scripts into web pages viewed by other users. These scripts can steal cookies, deface websites, or redirect users.
*   **How Phoenix Defends:** Phoenix's templating engine (EEx) automatically escapes content by default when using `<%= ... %>`. This converts special characters (like `<`, `>`, `&`) into their HTML entities, preventing them from being interpreted as executable code.
    *   Only use `<%= raw(...) %>` with extreme caution and on trusted input.

### 5. Insecure Direct Object References (IDOR)

*   **What it is:** Exposing internal implementation objects (e.g., database keys, filenames) directly to users, allowing attackers to manipulate or access unauthorized data by changing the reference in the URL or request parameters.
*   **How to Prevent:** Always implement proper authorization checks when an object is accessed via a user-supplied ID. Ensure the authenticated user has explicit permission to view or modify that specific resource.

### 6. Security Misconfigurations

*   **What it is:** Poorly configured server settings, default credentials, unpatched software, or unnecessary services can open doors for attackers.
*   **How to Prevent:** Regularly audit your application and server configurations. Change default credentials. Keep all software (OS, database, Elixir, Phoenix, dependencies) up-to-date. Disable unused features and services.

## Implementing Secure Coding Practices in Phoenix

1.  **Input Validation and Sanitization:**
    *   Always validate *all* user input on the server side using Phoenix changesets. Do not trust client-side validation.
    *   Sanitize input if it will be rendered back to the user (e.g., if allowing rich text, use a library to strip potentially malicious HTML tags).

2.  **Secure Database Interactions:**
    *   As discussed, always use Ecto's query builder. Never concatenate raw user input into SQL queries or raw Ecto query fragments without proper parameterization.

3.  **Output Escaping:**
    *   Leverage Phoenix's automatic HTML escaping (`<%= ... %>`). Use `raw/1` only when you are absolutely certain the content is safe (e.g., generated internally or has been rigorously sanitized).

4.  **Secure Session Management:**
    *   Configure `Plug.Session` with `secure: true` and `httponly: true` for production environments. This protects session cookies from being intercepted or accessed by client-side scripts.
    *   Implement proper session expiration and invalidation upon logout.

5.  **HTTPS Everywhere:**
    *   Enforce HTTPS for all traffic to encrypt data in transit. Use `Plug.SSL` in your endpoint to redirect HTTP to HTTPS.
    *   Configure your web server (e.g., Nginx, Caddy) to handle SSL termination.

6.  **Dependency Management and Auditing:**
    *   Regularly update your project dependencies (`mix deps.update`).
    *   Use `mix hex.audit` to check for known security vulnerabilities in your Hex dependencies.

7.  **Environment Variables for Sensitive Data:**
    *   Never hardcode sensitive information like API keys, database credentials, or secret keys directly in your source code. Use environment variables, especially with `config/runtime.exs`, to manage secrets securely.

8.  **Logging and Monitoring:**
    *   Implement robust logging for security-relevant events (e.g., failed login attempts, unauthorized access attempts).
    *   Monitor logs for suspicious patterns and set up alerts for critical security events.

## Quick Checklist/Exercise

1.  **CSRF Token Verification:** Open an existing Phoenix form in your application. Using your browser's developer tools, inspect the form to confirm the presence and correct formatting of the `csrf_input_tag()`. Try to submit the form after manually removing this hidden input via the developer tools; observe the application's response.
2.  **Ecto Query Review:** Identify a `Repo.all()` or `Repo.get_by()` call in your application that filters results based on user input. Confirm that the input is used as a parameter (e.g., `where: u.field == ^user_input`) rather than being interpolated into a raw string, ensuring SQL injection protection.
3.  **Input Validation Test:** Pick an endpoint in your application that accepts user input (e.g., creating a user, updating a profile). Use a tool like Postman or `curl` to send a request with intentionally invalid or malicious data (e.g., very long strings for a short text field, special characters where only alphanumeric are expected). Observe how your Phoenix application's changesets and validation rules handle these inputs, confirming they are rejected or sanitized correctly.
