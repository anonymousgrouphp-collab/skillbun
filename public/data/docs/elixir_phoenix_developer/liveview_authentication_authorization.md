# Authentication & Authorization with LiveView

Elixir Phoenix LiveView applications require robust mechanisms for managing user identity (authentication) and controlling access to resources and actions (authorization). While standard Phoenix controllers handle the initial login flow, LiveView brings unique considerations for maintaining user state and performing access checks in a stateful, real-time environment.

## 1. Core Concepts

### 1.1 Authentication in LiveView

Authentication ensures that users are who they claim to be. In LiveView, this typically involves:

*   **Initial Login:** User credentials are usually verified by a standard Phoenix controller and stored in the session using `Plug.Session`.
*   **Session Management:** The authenticated user's ID or relevant details are stored in the `Plug.Session` and made available to LiveView processes via the `socket.assigns` map.
*   **`on_mount` Callback:** This LiveView callback is crucial for performing initial authentication checks when a LiveView or LiveComponent is first mounted. It allows you to:
    *   Check for an authenticated user in the session.
    *   Redirect unauthenticated users.
    *   Assign user data to the `socket` for subsequent use.

### 1.2 Authorization in LiveView

Authorization determines what an authenticated user is permitted to do. This can range from showing/hiding UI elements to preventing server-side actions.

*   **`socket.assigns` for User Data:** Once authenticated, user-specific data (like `current_user` or `user_roles`) is assigned to the `socket`. This data is then used to make authorization decisions.
*   **Guarding UI Elements:** Use `if` or `unless` statements in your HEEx templates to conditionally render parts of the UI based on user roles or permissions.
*   **Guarding `handle_event` / `handle_info`:** Implement checks at the beginning of these callbacks to ensure the `current_user` has the necessary permissions before proceeding with an action. If not authorized, you can return `{:noreply, socket}` and potentially display an error message.
*   **`assign_new`:** A powerful LiveView function that allows you to fetch and assign data to the socket only if it doesn't already exist or if a condition is met. It can be used for fetching user-specific resources that the user is authorized to view.
*   **Plugs for Routes:** While `on_mount` handles LiveView-specific checks, standard Phoenix Plugs (e.g., `Plug.RequireAuthenticatedUser`) are still essential for protecting LiveView routes at the router level.
*   **External Libraries:** For complex authorization rules (e.g., role-based access control, attribute-based access control), consider libraries like `Pow` (which includes basic authorization features), or custom authorization modules.

## 2. Implementation Strategy

A common approach involves using `Phx.Gen.Auth` as a foundation and then extending it for LiveView:

1.  **Generate Authentication:** Use `mix phx.gen.auth Accounts User users` to scaffold a complete authentication system. This handles user registration, login, session management, and password resets.

2.  **Protect LiveView Routes:** Apply the `Plug.RequireAuthenticatedUser` plug (generated by `phx.gen.auth`) to your LiveView routes in `lib/your_app_web/router.ex`:

    ```elixir
    # lib/your_app_web/router.ex
    scope "/", YourAppWeb do
      pipe_through [:browser, :require_authenticated_user] # Protects all routes within this pipe

      live "/dashboard", DashboardLive, :index
      live "/profile", ProfileLive, :show
    end
    ```

3.  **Integrate User into LiveView:** `Phx.Gen.Auth` typically sets up a global `on_mount` hook in `lib/your_app_web.ex` that automatically assigns `current_user` to the socket if authenticated. For example:

    ```elixir
    # In lib/your_app_web.ex (part of the YourAppWeb module)
    def on_mount(:current_user, _params, session, socket) do
      if user = Accounts.get_user_by_session_token(session["user_token"]) do
        {:cont, assign(socket, :current_user, user)}
      else
        # User not authenticated, redirect to login
        {:halt, socket |> Phoenix.LiveView.redirect(to: ~p"/users/log_in")}
      end
    end
    ```
    Then, ensure your LiveViews use this hook (e.g., via `use YourAppWeb, :live_view` which often includes it, or explicitly `on_mount :current_user` in your LiveView).

4.  **In-LiveView Authorization Checks:** Use the `current_user` assigned to the socket to perform granular authorization.

    ```elixir
    # lib/your_app_web/live/dashboard_live.ex
    def mount(_params, _session, socket) do
      # :current_user is assumed to be already assigned by a global on_mount hook
      {:ok, socket}
    end

    def handle_event("delete_item", %{"item_id" => item_id}, socket) do
      if socket.assigns.current_user && has_permission?(socket.assigns.current_user, :delete_item) do
        # Perform deletion logic
        {:noreply, socket |> put_flash(:info, "Item deleted successfully.")}
      else
        # Not authorized
        {:noreply, socket |> put_flash(:error, "You are not authorized to delete this item.")}
      end
    end

    defp has_permission?(user, permission) do
      # Implement your permission logic here, e.g., check user roles or specific attributes
      user.is_admin # Simple example: Check if user is an admin
      # Or: Enum.member?(user.roles, :admin)
    end
    ```
